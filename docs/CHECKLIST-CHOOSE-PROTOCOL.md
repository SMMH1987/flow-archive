# چک‌لیست یک‌صفحه‌ای: برای هر سرویس کدام روش اتصال؟

برای هر سرویس/پروژهٔ تازه، یک بار پر شود و نتیجه در `capabilities.yaml` (فیلد `protocol`) ثبت شود.
وضعیت: پیشنهاد (جمع‌بندی یافته‌های `PROJECT-INTEROP.md`)؛ خودِ درخت تصمیم برداشت من است، نه استاندارد رسمی.

## پیش‌فرض ثابت (دیگر پرسیده نمی‌شود)
هر سرویس باید همیشه با دو خانواده مصرف‌کننده سازگار باشد:
1. **سازگار با Claude:** سرور MCP روی Streamable HTTP (Claude Code، claude.ai، Claude API).
2. **سازگار با OpenAI:** REST با OpenAPI و تعریف ابزار به قالب OpenAI (`{"type":"function","function":{name, description, parameters}}`)؛ همین قالب را مدل‌های دیگر و OpenRouter می‌فهمند و برنامهٔ مصرف‌کننده ابزار را خودش اجرا می‌کند.

یک بار تعریف، دو خروجی: schema هر ابزار را یک جا (JSON Schema) بنویس و از آن هم `inputSchema` برای MCP و هم `parameters` برای قالب OpenAI و هم OpenAPI را بساز. مغز سرویس از این لایه‌ها جدا بماند.

**هر سرویس همیشه دو حالت اجرا دارد (پرسیده نمی‌شود):**
- **لوکال:** روی `127.0.0.1` (HTTP یا stdio) برای Claude Code و برنامه‌های همان ماشین؛ پیش‌فرض توسعه.
- **عمومی:** همان کد پشت HTTPS عمومی (سرور، یا تونل موقت) برای claude.ai، Claude API، Grok و بات‌های ابری، با احراز هویت و سقف نرخ.
فقط با تنظیمات عوض می‌شود: `HOST`/`PORT`، `PUBLIC_BASE_URL`، `AUTH_REQUIRED`؛ کد و ابزارها یکی است. لوکال بدون کلید ولی فقط روی `127.0.0.1`؛ عمومی همیشه با کلید.

## گام ۱ — فقط یک پرسش
| # | پرسش | پاسخ |
|---|---|---|
| ۱ | پرخطر است؟ (پول، قرارداد، امضا، انتشار، حذف) | بله / خیر |

«شکل کار» دیگر پرسیده نمی‌شود: هر ابزار هر سه حالت را با یک پاکت پاسخ یکسان پشتیبانی می‌کند (بخش پایین).

## پاکت پاسخ یکدست (هر ابزار، هر بار)
```json
{ "status": "done | needs_input | processing",
  "request_id": "...", "case_id": "...",
  "result": { ... },                       // فقط وقتی done
  "question": { "id": "...", "text_fa": "..." },   // فقط وقتی needs_input
  "retry_after_s": 5, "queue": 2 }         // فقط وقتی processing
```
- شرایط ساده: همان لحظه `done`.
- سرویس اطلاعات کم دارد: `needs_input` با سؤال بعدی؛ مصرف‌کننده جواب می‌دهد و ادامه می‌دهد.
- کار طول می‌کشد: `processing` (در REST کد `202`)؛ مصرف‌کننده بعد از `retry_after_s` همان درخواست را دوباره می‌زند یا وب‌هوک می‌گیرد.
هر بار خود سرویس تصمیم می‌گیرد کدام حالت؛ مصرف‌کننده فقط `status` را می‌خواند. این شکل با وضعیت‌های A2A (COMPLETED، INPUT_REQUIRED، WORKING) هم‌خوان است و حق‌پرس فعلی تقریباً همین را دارد (`state()` و `202 processing`).
